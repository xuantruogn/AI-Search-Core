TASK: Redesign the product-limit/subscription recovery and product synchronization lifecycle.

IMPORTANT BUSINESS RULE:

A product that has already been indexed/vectorized MUST NOT have its vector/index data deleted merely because the shop's plan/product limit was reduced, subscription became inactive, or the product temporarily became ineligible due to quota.

Plan limits control whether a product is ACTIVE/SEARCHABLE, not whether cached vector data is physically retained.

Only a real Shopify product deletion should hard-delete the product/vector.

CURRENT BUG:

When productLimit is lowered below the number of indexed products, the indexed count falls and later rises again.

The current recovery service queues blocked products as:

topic: "PRODUCTS_UPDATE"

This causes quota recovery to enter the normal Shopify product-update indexing pipeline and may execute:

Shopify processing
→ GPT product enrichment
→ embedding
→ vector write
→ indexed

This must stop.

The existing recoverBlockedProducts() currently handles:
- subscriptionBlockedProducts
- vectorQuotaBlockedProducts
- productLimitBlockedProducts

and calls enqueueProductSyncJob(... topic: "PRODUCTS_UPDATE").

Do not patch only this one function. Inspect the full lifecycle and fix the architecture consistently.

Inspect at minimum:

- commerce/entitlement.server.ts
- commerce/indexed-products.server.ts
- product-indexer.server.ts
- product-sync-job.server.ts
- product-sync-queue.server.ts
- current product webhook handlers
- all callers of recoverBlockedProducts()
- all callers of recoverQuotaBlockedProducts()
- code that handles productLimit changes
- code that counts productSlotsUsed
- vector search filtering
- Prisma models for indexed products/jobs/settings/usage

==================================================
1. SEPARATE VECTOR STATE FROM SEARCH ELIGIBILITY
==================================================

A product must conceptually have two independent state dimensions:

Vector/data state:
- MISSING
- READY
- STALE
- ERROR

Search eligibility:
- searchable = true/false
- blockedReason for diagnostics, e.g.
  PRODUCT_LIMIT
  SUBSCRIPTION
  UNPUBLISHED
  OTHER

Use existing schema fields if equivalent fields already exist.
Do not create duplicate concepts unnecessarily.

If schema changes are needed, add the minimum fields required.

Important:
blockedReason is diagnostic.
The desired eligibility should be recomputable from current catalog state + current policy.
Do not rely only on the historical blockedReason to decide future eligibility.

==================================================
2. PRODUCT LIMIT APPLIES TO ACTIVE PRODUCTS ONLY
==================================================

productLimit must represent the maximum number of products allowed to participate in AI Search.

It must NOT represent the maximum number of cached vectors stored.

Example:

catalog products      = 1283
cached vectors        = 1283
productLimit          = 100
searchable products   = 100
blocked by limit      = 1183

This state is valid.

Audit the current meaning of entitlement.productSlotsUsed.

If productSlotsUsed currently counts indexed rows or vector records, change/refactor it so the entitlement check uses ACTIVE/SEARCHABLE product slots.

Expose separate counts where useful:

activeProductSlotsUsed
cachedVectorCount
blockedProductCount

Do not decrement historical usage counters when deactivating products.

==================================================
3. LOWERING PRODUCT LIMIT
==================================================

Example:

oldLimit = 10000
newLimit = 100
currently searchable = 1283

Expected behavior:

- acquire a shop-level policy reconciliation lock
- read the latest policy
- determine desired active product set deterministically
- keep exactly 100 eligible products searchable
- mark the other 1183 as searchable=false / PRODUCT_LIMIT blocked
- KEEP their vector data
- KEEP their embedding metadata/content hashes
- do NOT call GPT
- do NOT call embeddings API
- do NOT enqueue PRODUCTS_UPDATE
- do NOT delete vectors
- do NOT increment vector usage

Changing a plan/limit is a POLICY RECONCILIATION operation, not a product-sync operation.

Use deterministic ordering when deciding which products stay active.

Prefer preserving the currently active set to minimize churn.
Use an existing stable field such as indexedAt/createdAt/productId as tie-breaker if suitable.

Do not randomly change which products occupy the available slots on every reconciliation.

==================================================
4. INCREASING PRODUCT LIMIT
==================================================

Example:

oldLimit = 100
newLimit = 500

There are 1183 product-limit-blocked products.

Open 400 additional slots.

For each newly eligible product:

If:
- vector exists
- vector status READY
- product content has not changed

Then:
- simply searchable=false → searchable=true
- no GPT
- no embedding
- no vector quota usage

If:
- vector missing
or
- vector status STALE

Then:
- product becomes eligible for reindex
- enqueue a dedicated REINDEX_PRODUCT job
- consume vector quota only when an actual vector write occurs
- after successful reindex mark READY + searchable

Do not enqueue PRODUCTS_UPDATE for simple quota recovery.

==================================================
5. PRODUCT WEBHOOK WHILE PRODUCT IS BLOCKED
==================================================

If a product is not searchable because of PRODUCT_LIMIT or SUBSCRIPTION and Shopify sends PRODUCTS_UPDATE:

Do not blindly run expensive enrichment/embedding.

Update the local product metadata needed to detect change.

Calculate/update the existing content hash using the current project conventions.

If content changed:
- vectorStatus = STALE

Keep:
- searchable = false

Do NOT call GPT/embedding while the product is ineligible solely to keep an unused vector fresh.

When it later becomes eligible:
- READY vector → activate immediately
- STALE/MISSING → reindex then activate

Preserve existing behavior for genuinely active products unless this task requires changing it.

==================================================
6. SUBSCRIPTION STATE
==================================================

Subscription inactive:

- products become non-searchable according to policy
- vectors are retained
- no mass re-embedding
- no vector deletion

Subscription active again:

- run policy reconciliation
- reactivate cached READY vectors immediately
- only enqueue reindex for products whose vectors are STALE/MISSING

The current subscription recovery branch must no longer queue 50 generic PRODUCTS_UPDATE jobs.

==================================================
7. VECTOR UPDATE QUOTA IS INDEPENDENT
==================================================

productLimit = capacity
vectorUpdateLimit = number of actual vector update operations allowed

Do not couple them.

Activating an existing READY vector:
- must NOT consume vectorUpdateLimit

Deactivating due to productLimit:
- must NOT consume vectorUpdateLimit

Only actual vector creation/update increments vector usage.

If vector quota is exhausted and an active/eligible product becomes stale:
- preserve the old vector according to existing safe behavior
- record STALE / vector-quota-blocked state
- do not pretend that product capacity itself has been consumed by a vector operation

Review all existing vector quota checks for this distinction.

==================================================
8. REPLACE GENERIC RECOVERY
==================================================

Refactor recoverBlockedProducts().

Preferred high-level behavior:

recoverBlockedProducts(shop)
    → reconcileProductEligibility(shop)
    → immediately activate eligible cached READY products
    → identify eligible products that are MISSING/STALE
    → enqueue only dedicated reindex jobs within current vector budget

It must NOT represent quota recovery as a fake Shopify PRODUCTS_UPDATE event.

If the existing job table requires a topic/kind, introduce/reuse explicit job semantics such as:

SHOPIFY_PRODUCT_UPDATE
REINDEX_PRODUCT

Policy reconciliation should preferably not require a product job at all when it is only changing eligibility flags.

Preserve backward-compatible exported function names temporarily if older routes import recoverQuotaBlockedProducts, but route them to the new logic.

==================================================
9. STALE JOB PROTECTION / POLICY VERSION
==================================================

There may already be many queued jobs created under an older limit.

Prevent them from restoring products after the limit has changed.

Introduce or reuse a per-shop policy/version/generation concept.

Example:

policyVersion 41:
productLimit=10000

then limit changes:

policyVersion 42:
productLimit=100

A job created under version 41 must not blindly index/activate a product under version 42.

At execution time:
- compare job policy version / current policy
or
- always re-evaluate current eligibility atomically immediately before the expensive operation and before activation.

Prefer explicit policyVersion if it fits the current schema.

Stale jobs should be discarded or re-evaluated safely.

10. SHOP-LEVEL RECONCILIATION LOCK
==================================================

Current per-product locks are insufficient to protect the invariant:

activeProductCount <= effectiveProductLimit

Ensure only one product-policy reconciliation per shop runs at once.

A limit decrease and a recovery/increase operation must never fight each other.

If the policy changes during an existing reconciliation:
- detect version mismatch
- stop/retry using the newest policy

Do not allow:
DOWN reconciliation
and
UP recovery

to run independently against stale snapshots.

==================================================
12. SEARCH FILTERING
==================================================

Because vectors for blocked products remain stored, vector search MUST exclude non-searchable products.

Check the current search retrieval implementation.

Preferred:
filter at vector-query/retrieval time by:
- shop
- searchable/eligible product

Do not retrieve only top K from all vectors and then remove blocked products afterwards, because blocked vectors may consume the entire top K.

If the current vector store cannot filter on eligibility directly, implement a safe eligible-product restriction using the current architecture.

A product blocked by productLimit/subscription must never appear in storefront AI results.

==================================================

Real Shopify product DELETE:

Unpublished/non-searchable catalog state:

Do not confuse real catalog deletion with plan downgrade.
